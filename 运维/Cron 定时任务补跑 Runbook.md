# Cron 定时任务补跑 Runbook

> 上级入口：[[运维/运维 MOC|运维 MOC]]、[[AI/Agent/Agent 运行失败分级与重试策略|Agent 运行失败分级与重试策略]]。

## 适用场景

用于定时任务因 LLM 上游失败、runner 启动超时、网关重启、投递失败而未完成时的人工补跑。目标是补齐产物，同时避免并发过高导致二次故障。

## 操作原则

1. 先列任务，再看最近运行记录，不凭记忆补跑。
2. 排除高频心跳类任务，避免刷屏或制造失败风暴。
3. 按低并发分批补跑，建议每批 2-3 个。
4. 等待第一批进入运行或完成后，再补下一批。
5. 补跑后核验产物路径或投递状态。

## 分批策略

- 轻量任务：可 3 个并发。
- 大报告任务：建议 1-2 个并发。
- 依赖同一模型上游：如果连续出现 LLM request failed，暂停 15-60 分钟。
- 出现 isolated agent setup timed out：说明 runner 压力过大，应降低并发。

## 记录字段

补跑报告应包含：任务名、job_id、run_id、触发时间、是否入队、是否完成、失败原因、是否需要下一轮补跑。

## 验证

- 查看 run history 最新一条是否为 ok。
- 查看输出文件是否更新。
- 查看 QQ/消息投递是否 delivered。
- 对日报类任务，确认日期没有错位。

## 风险

并发补跑可能消耗大量 token、触发 rate limit、放大 provider 故障。必要时优先补关键任务，把低价值日报延后。
